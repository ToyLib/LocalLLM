# ChatGPT 連携の設計メモ

ローカルの LLM (llama-server) に加えて、ChatGPT (OpenAI API) も使えるようにするための方針です。
実装済みです。使い方は [chatgpt.md](chatgpt.md) を参照してください。

実装では、次の点をこのメモから変えています。

- `server.json` は接続先プロファイルの一覧にせず、今までの `chat_url` / `embed_url` (ローカル) はそのまま残して、`cloud` を足しました。前の版の設定ファイルもそのまま読めるようにするためです。
- 書き直すかどうかは、回答役ごとの `rewrite` (agents.json) で決めます (既定: アシスタントはしない、侍はする)。回答役の人格をテンプレートで変えられるため、「アシスタントなら書き直さない」と決め打ちにしませんでした。
- ChatGPT の system プロンプト (`cloud`) と書き直しの指示 (`rewriter`) も agents.json に置き、設定画面で変えられるようにしました。
- Python 版 (Tk) にはツールチップが無いので、押せない理由などはボタンの横に書きます。

## 1. 対応範囲

| 区分 | 内容 |
| --- | --- |
| 今回 | ローカル (llama-server) と ChatGPT (OpenAI API) |
| 後回し | Azure OpenAI (API キー方式、v1 形式の URL を想定) |
| 対応しない | Entra ID 認証 |

- C++ 版・Python 版の両方に同じ機能を入れます。
- `doc/` と README も合わせて更新します。

## 2. 接続先の設定

`server.json` を「接続先プロファイル」の一覧にし、エージェントがどのプロファイルを使うかを選べるようにします。

```json
{
  "profiles": {
    "local": {
      "provider": "llamacpp",
      "chat_url": "http://127.0.0.1:8080/v1/chat/completions",
      "embed_url": "http://127.0.0.1:8081/v1/embeddings"
    },
    "openai": {
      "provider": "openai",
      "chat_url": "https://api.openai.com/v1/chat/completions",
      "chat_model": "gpt-5",
      "auth": "bearer",
      "api_key_name": "OPENAI_API_KEY"
    }
  }
}
```

(項目名は実装時に決め直してよい。)

- 認証ヘッダーの形式 (`none` / `bearer` / `api-key`) をプロファイルで切り替えられるようにしておく。`api-key` は後で Azure OpenAI に使う。
- 今は固定の `"model": "local"` / `"embed"` を、プロファイルのモデル名にする (llama-server はこの値を無視するので、ローカルは今のままでよい)。
- llama-server 専用の項目は OpenAI に送らない。
  - `chat_template_kwargs` (考えずに答えさせる設定) は送らない。
  - `max_tokens` は、モデルによって `max_completion_tokens` に切り替える。
  - `temperature` を受け付けないモデル (推論モデル) では外す。
- JSON スキーマ (`response_format`) には、OpenAI 向けに `"strict": true` と `"additionalProperties": false` を付ける。
- Python 版の `llm_client.py` は `HTTPConnection` 固定で、URL のパスしか送っていない。
  - `https` なら `HTTPSConnection` を使い、ポートの既定を 443 にする。
  - パスにクエリ文字列も付けて送る (後で Azure の `api-version` に必要)。
- C++ 版は libcurl に URL をそのまま渡しているので、HTTPS もクエリもそのまま動く。

## 3. API キーの管理

設定ファイルにはキーの**値を書かず、名前だけ**を書きます (`api_key_name`)。
そのため `server.json` は今までどおり、git に入っても設定画面で保存しても問題ありません。

### キーを探す順番

1. 同じ名前の環境変数 (例: `OPENAI_API_KEY`)
2. ユーザーごとの秘密ファイル
3. 見つからなければ「API キーが設定されていません」

macOS では、Finder から起動したアプリはシェルの環境変数を読まないので、環境変数だけでは足りません。秘密ファイルも必要です。

### 秘密ファイル

リポジトリやビルドフォルダの外に置きます。C++ 版では `SDL_GetPrefPath` で場所を取ります。

| OS | 場所 |
| --- | --- |
| macOS | `~/Library/Application Support/LocalLLM/secrets.json` |
| Linux | `~/.config/LocalLLM/secrets.json` |
| Windows | `%APPDATA%\LocalLLM\secrets.json` |

- macOS / Linux では、作るときに権限を `0600` にする。
- `config/`、`build/config/`、`user-config/` には置かない (ビルド時のコピーや git、zip での受け渡しに混ざらないように)。

### 設定画面

- パスワード入力欄にして、操作は「登録」と「削除」だけにする。
- 登録済みのときは「設定済み (…abcd)」と末尾 4 文字だけを表示し、キー全体は画面に出さない。
- 保存先は秘密ファイル (`server.json` には書かない)。

### 漏れ防止

- 認証情報を送るのは **https の URL のときだけ**。URL を `http://127.0.0.1` に戻したときに、ほかのサーバーへキーを送らないようにする。
- ログやエラー表示に、リクエストのヘッダーやキーを出さない。
- アプリの外での対策として、OpenAI の管理画面でこのアプリ専用のプロジェクトキーを作り、利用上限を設定しておく。漏れたらそのキーだけを無効にする。

OS のキーチェーン (macOS Keychain / Windows 資格情報マネージャー / Linux libsecret) は、後から「キーを探す順番」に足せる作りにしておきます。今回はやりません。

## 4. マルチエージェントの流れ

ふだんはローカルで答え、物足りないときだけユーザーがボタンで ChatGPT に聞き直します。
ChatGPT の答えは、ローカルの回答役 (侍など) が自分の口調で言い直して表示します。

```
質問 → ルーター (ローカル) → 回答役 (ローカル: アシスタント / 侍など) が答える
   ↓ ユーザーが「ChatGPT に聞き直す」を押す
ChatGPT が答えを作る (全部受け取るまで画面には流さない)
   ↓
同じ回答役がローカルで口調を書き直す → ストリーミングで表示
```

- **ルーターと RAG の検索はローカルに固定**する。ルーターに渡す資料の一覧 (ファイル名と見出し) も個人データなので。
- ChatGPT に送るのは、ユーザーがボタンを押したときだけ。

## 5. 「ChatGPT に聞き直す」ボタン

- **最新の回答の下だけ**に付ける (過去の回答にも付けると、履歴が枝分かれして扱いが複雑になる)。

### 押せないとき (グレーアウト)

| 条件 | ツールチップ |
| --- | --- |
| API キーが未設定 | 設定画面で API キーを登録すると使えます |
| 回答の受信中・書き直し中 | (なし) |
| 回答がエラーで終わった | (なし) |

- ImGui の `BeginDisabled` と `SetItemTooltip` (`ImGuiHoveredFlags_AllowWhenDisabled`) で、押せないボタンにもツールチップを出す。
- キーの有無は、起動時と設定画面で保存したときに調べて覚えておく (毎フレームファイルを読まない)。登録した直後から押せるようにする。
- 見ているのはキーがあるかどうかだけ。キーが無効なら、押した後に 401 のエラーを分かりやすく表示する。

### 資料を使った回答のとき

確認ダイアログを出してから送ります。

> 資料 (rag/) の内容が ChatGPT に送られます。送りますか？

## 6. 送る内容と会話履歴

- 履歴のメッセージに「資料を使った (非公開)」の印を付ける。
- ChatGPT 宛ての履歴からは、**非公開のターンを除く**。
- 聞き直す対象のターン自体が資料を使っているときは、確認のうえで、そのターンの質問と資料を送る。
- 聞き直した後は、ローカルの最初の回答を LLM 用の履歴から外し、書き直した回答だけを残す (食い違う答えが 2 つ残ると、次の質問で混乱するため)。
- 画面には、最初の回答を薄く表示して残す。

## 7. 口調の書き直し

- 回答役の system プロンプトに加えて、次のように指示する。
  - ChatGPT の回答を、自分の口調で言い直す。
  - 内容・数値・手順・固有名詞・コードは変えない。足したり削ったりしない。
- 回答役が**アシスタント (普通の丁寧語) のときは書き直さず**、ChatGPT の回答をそのまま表示する。
- ChatGPT の元の回答は**折りたたみで見られる**ようにする (小さいモデルの書き直しで中身が変わっていないか、確かめられるように)。
- 書き直しに失敗したら、ChatGPT の回答をそのまま表示する。

## 8. エラー

| 起きたこと | 動き |
| --- | --- |
| ChatGPT が 401 (キーが無効) | 最初の回答はそのまま。「API キーが無効です」と表示 |
| ChatGPT が 429 (回数制限・残高不足) | 最初の回答はそのまま。制限か残高不足と表示 |
| ネットワークエラー | 最初の回答はそのまま。エラーを表示 |
| ローカルの書き直しが失敗 | ChatGPT の回答をそのまま表示 |
| 中断ボタン | どの段階でも止められるようにする |

OpenAI のエラー本文は `{"error": {"message": ...}}` の形なので、`message` を表示する。

## 9. 画面表示

- 回答の上のエージェント名に、接続先を添える。
  - ローカルだけ: `侍`
  - 聞き直し: `侍 (ChatGPT → ローカルで書き直し)`
  - 書き直しなし: `アシスタント (ChatGPT)`
- 状態を「ChatGPT に問い合わせ中… → 侍が言い直し中…」のように表示する。

## 10. 後回しにすること

- Azure OpenAI 対応 (`api-key` ヘッダー、デプロイ名をモデル名にする、コンテンツフィルターで止められたときの表示)
- OS のキーチェーン
- ルーターによる難しさの自動判定 (ボタンの代わりや補助として)
- 使ったトークン数・料金の表示
- RAG の埋め込みを OpenAI にすること (今回はローカルのまま。モデルを変えると保存済みのベクトルが使えなくなる点に注意)
